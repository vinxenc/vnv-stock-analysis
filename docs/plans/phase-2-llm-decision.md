## Goal

For each symbol of the day's Phase 1 ranking with a score of 40 or more, **three deciders answer buy or skip, with a probability**, in three pipelines (GitHub Actions jobs) that run one after another, `llm` then `decision_model` then `tabular`, and start only once a filter job has written the day's input as one JSON file:

| Decider | Kind | Reads | Runs |
|---|---|---|---|
| **Claude** | LLM, API (through OpenRouter, behind the `LLMProvider` interface) | one symbol's data as JSON | API call per symbol |
| **Jev** (TypeSafe) | decision model, API | the same JSON as state, one typed question | API call per symbol |
| **TabICL** | tabular foundation model, open source (BSD-3) | the symbol's feature row, with the labelled history of all symbols as context | on the runner's CPU |

Every answer is stored in `vn_stock_decisions`; five sessions later the outcome is filled in, so the three are measured on the same rows. Once all three have answered, **one Telegram message** with the session's decisions goes to one channel.

The decisions are the system's output for the user to screen with; the user decides what to trade.

- [x] A row is filled only when the symbol has a bar on `t` and on each of the 5 market sessions after it, and no one-day change between them is beyond `MAX_MOVE` (review-debt item 11). Then `return_5 = close(t+5) / close(t) − 1` and `hit = close(t+5) ≥ close(t) × 1.03`, computed in `numeric` so an exact +3% counts. `hit` is set for `skip` rows too: it means "the price reached +3%", not "the decision was right" (step 9's base rate needs the `skip` rows). Otherwise the row stays empty:
  - A symbol halted on `t+5` stays empty, even if it trades again later (counting its own bars would pick a later bar).
  - A missing bar in between would make one "one-day" change span two sessions, so the row stays empty too, until that bar is stored.
  - A session the sync missed for every symbol is absent from the stored dates, so `t+5` counted in them would be the sixth real session (PR #34 review). The working days of the holiday calendar (`scripts/vn_holiday.py`, as the screen uses) in (`t`, `t+5`] must also number 5; otherwise the row stays empty until the missing session is stored. A holiday the calendar does not know only leaves a row empty, never fills it wrong; `CLOSURES` in `vn_holiday.py` adds the ones the `holidays` package misses (2026-01-02, the only one among the stored weekdays since 2025-01-02). A session the sync commits while the job runs is past the calendar's last day and is left for the next run.
  - A move beyond 7.5% cannot be a real HOSE session (band ±7%, kept with a margin so a ceiling close is not dropped): it is an ex-rights date on adjusted prices, where the stored closes of `t` and `t+5` are adjusted as of different days and would give a fake miss.
  - Known limit: an adjustment under 7.5% (a cash dividend) still passes and skews `return_5` by its size. The first session after a listing (±20%) or after a long halt is dropped too.
